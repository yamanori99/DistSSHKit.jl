Packages

This page is the list the release rules read. Adding a package is one row here, plus the checks in Releasing.

Release in dependency order: a package after everything it depends on. Wait until General merges each release before the next. Today that is DistSSHRun, then DistSSHQueue, then DistSSHKit.

PackageDepends onReexportsInstalled on its ownCompat filesOrdinary pathBefore register

testenv/example-job/Project.toml in DistSSHQueue pins DistSSHRun at "0.1.2". Raise that floor only when an older DistSSHRun lacks a fix that example promises. It is not part of every Queue cut.

DistSSHKit's required checks are the ones named in the table. A version-cut pull request runs the full suite. Path filters do not apply. A main push that only raises version and updates NEWS.md does not re-run Test. Register from the green pull request.

cut-hold is on DistSSHRun and DistSSHQueue. A red Linux job in a scheduled E2E weekly run (daily) adds it to the Issue E2E weekly failed. Intel and WSL do not. A later green scheduled Linux removes it, even if Intel or WSL is still red. The Issue stays open until a whole run is green. DistSSHKit has no cut-hold.

When a package breaks something public, every package that reexports it raises its minor too. A package that depends on it without reexporting raises only its compat, in a patch, unless the change leaks into its own public API. A change in an upper package never raises a lower one.

A breaking release of a package that many others depend on is a release of all of them together. Keep that package small. Today DistSSHBase and DistSSHUp are submodules of DistSSHRun (DistSSHRun.DistSSHBase and DistSSHRun.DistSSHUp), not separate packages. DistSSHQueue and DistSSHKit use those submodules. If they are later split out and registered, DistSSHUp would depend on DistSSHBase and be installed on its own. DistSSHKit would depend on both and reexport neither. Both would start at 0.1.0. Add the row before the first release.

Rules for 1.0 are not decided.
